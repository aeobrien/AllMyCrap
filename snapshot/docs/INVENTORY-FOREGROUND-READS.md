# Automatic inventory reads — local prototype

A synthetic client can submit a read, the foreground Swift worker receives it over HTTP, the existing reader reads its explicitly supplied SwiftData store, and the reply returns to the same client. No manual copying is involved. This source slice does not install a live phone connection.

The actual app target includes the reader, typed protocol, retained owner, URLSession transport and foreground worker. The app constructs the worker from its existing mainContext and forwards scene activation changes. No production pairing/configuration source is supplied, so the installed app path remains unconfigured and makes no inventory-session network calls. Store creation, backup and review-expiry behavior are unchanged. The fixture host never initializes that ordinary App or BackupManager.

## Ownership and read operations

Configuration must explicitly supply device/store/client identities and a transport factory. These IDs in tests are generated synthetic identities, not durable production store identity. Each activation generates a new worker scope and reader instance; one instance is retained across that active session so pagination works. There is one polling task. Duplicate activation cannot start another, inactivity cancels/invalidates its transport, and owner release cancels the task. Late completion from an inactive generation cannot initiate a result publication. Already transmitted network bytes cannot be recalled; replies remain bound to the old request/scope and cannot satisfy a different one.

Only status, list(items/locations/tags with archive/page/cursor) and show(kind/exact UUID) are supported. Unknown keys/versions/operations fail before reading. No request contains a model query, executable, file/store path or arbitrary target URL. Pending UI edits remain pending and produce pendingEdits. Read failures stay explicit; they never become an empty successful inventory. Underlying store error details are replaced with readUnavailable to avoid disclosing paths. Every response preserves transactionalSnapshot=false.

All requests bind version, request UUID, canonical-body SHA256, client, device, store and current scope. Canonical request JSON is UTF-8 sorted keys with compact separators and literal slashes, no duplicate keys/nonfinite numbers; shared Swift/Python checks recompute its digest. Dates in response data need not have byte-identical floating-point serialization between Swift and Python; response parsing still rejects duplicate keys, invalid JSON and over-limit bodies. Request canonicalization is unchanged by that distinction.

## Local mailbox and client

`tools/inventory_session/mailbox.py` is an in-memory, loopback-only prototype with distinct generated client and worker bearer credentials. It authenticates roles, selects only the configured binding and preserves first completed replies. Same request ID/body returns its retained state/result; changed body conflicts. Readback can recover a retained completion while the worker is offline. Expired IDs become tombstones until worker-scope reset; they are not silently rerun. This is not durable exactly-once execution or restart recovery.

Limits:16KiB requests,2MiB encoded reply envelopes (reader result limit remains1MiB),32 retained request IDs per scope,300-second retention, one claimed request at a time from the sequential Swift worker,1-second polling,4-second worker liveness grace and eight concurrent HTTP request handlers. Each accepted handler has an absolute three-second deadline starting before request-line/header parsing; its owned socket is shut down on expiry even if headers or body bytes keep arriving. The handler then releases its capacity slot. This prototype does not promise uninterrupted service under a sustained connection flood. Inactivity immediately stops local polling; mailbox unavailable status follows its finite liveness grace. Metadata/error counts are bounded; no credential or inventory body is logged. A new activation invalidates old queued requests/cursors by scope.

The prototype client requires an explicit literal-loopback endpoint, token file and read-argument file; there is no host/account/backup discovery or installed global command. Its overall wait is at most30 seconds, each HTTP request has a wall-clock body budget up to3 seconds, and redirects/proxies are not followed. Explicit cancellation marks a request cancelled; a deadline stops waiting and may leave its bounded mailbox request pending, which can later be inspected/retried with its original ID. Deadline is not proof the worker never read. The mailbox refuses a response to a cancelled/expired request. Transport loss is unavailable, not success.

The Swift transport uses ephemeral URLSession, no cookies/cache, explicit endpoint, no redirect following and incremental bounded body reads. Plain HTTP requires explicitly allowed literal127.0.0.1; production would require a separately approved HTTPS endpoint/authentication/pairing implementation. No ATS relaxation was added.

## Verification and remaining delivery

`tests/inventory_session_protocol.py` compiles the actual models, reader, owner, worker and transport with isolated temporary stores; it does not run the App. `tests/inventory_session_roundtrip.py` uses a real local mailbox/client and separately compiled Swift fixture process running the actual URLSession worker. Synthetic control files alter only that fixture's store/lifecycle. Separate HTTP listeners prove redirects do not deliver a body or credential to another origin. The actual unsigned iOS app target is built separately without simulator boot or app launch.

The existing hosted Xcode unit-test target has no registered tests and starts the real App, so this slice does not run it or count it as evidence. Mac fixture execution plus iOS product compilation is not physical device/iOS lifecycle acceptance. Before sessions can access possessions: select/deploy the real mailbox, add durable device/store pairing and credential custody/revocation, configure the app, verify the installed build/foreground behavior with the user, and prove fresh Claude/Codex discovery. There are no mutation endpoints, added approval rituals for reads, changed add/remove approval rules, remote deployment or personal data operations in this slice.
