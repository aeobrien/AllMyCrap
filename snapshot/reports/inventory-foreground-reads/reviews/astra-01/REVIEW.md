## Blocking fault: incomplete HTTP requests can exhaust every handler forever

`tools/inventory_session/mailbox.py:129–140` installs its socket timeout only inside do_POST, after BaseHTTPRequestHandler has parsed the request line and headers. At:149–157, eight handlers consume all semaphore slots until each handler exits. A connection that sends a request line but never completes its headers has no timeout, so eight such connections indefinitely deny every normal client/worker request. The timeout after headers is also a socket inactivity timeout, not a total deadline: a trickled body can prolong occupancy.

Independent probe_http_stall.py creates the actual maintained loopback server with synthetic identities/credentials and an injected fixed liveness clock. A normal authenticated hello succeeds first. Eight sockets then send only `POST /client/hello HTTP/1.1\r\n`; after4.2seconds a normal hello fails transport. Understudy http-stall-01 records expected-success failure in4.850seconds, untruncated/no timeout. Every owned socket is closed afterward and the server shuts down. The fixed clock prevents worker liveness expiry from explaining the failure. Static control flow establishes that the unfinished headers have no later timeout at all.

This violates the planned finite request waits and lets incomplete local connections permanently disable the prototype, even though retained rows and handler count are bounded. Install a whole-request deadline covering request line, headers and body, release capacity on timeout, and prove recovery for silent/incomplete and continuously trickled input. A timeout only after headers, or reset on each received byte, is insufficient. Author and parent were informed immediately; retain this original red.
